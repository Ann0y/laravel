## 1. 项目概述

面向中小型景区，构建一套 B/S 架构的前后端分离售票与票务管理系统，替代"窗口排队买票 + 纸质门票 + 手工统计"的传统方式：

- **全程闭环**：购票 → 出票 → 检票 → 退票（/ 改期 / 评价），全流程状态可视、可追溯；
- **限量可控**：按"园区开放日 × 票种"设置每日售票额度，售票时做库存校验与防超卖控制；
- **检票有序**：门票含唯一核销码（二维码 / 编码），核销时校验有效期与状态，防重复使用；
- **数据决策**：管理端可视化看板（售票量 / 入园量 / 收入 / 退票率），游客端本人购票概要图表。

范围边界：

| 纳入范围 | 不纳入范围 |
| --- | --- |
| 票种与额度管理、在线购票、门票核销、退票审核、统计报表、游园评价 | 真实支付网关（本期模拟支付）、短信 / 电子发票、闸机硬件 |
| Web 端（PC + 移动端自适应）、三角色功能 | 原生 App / 小程序、多景区集团化管理、客流预测与动态定价 |

## 2. 用户角色与入口

| 角色 | 来源 | 核心职责 | 入口 |
| --- | --- | --- | --- |
| **游客** | 前台自助注册 / 后台建号 | 浏览票种、在线购票、订单门票、退票申请（门票改期）、游园评价 | 游客端 |
| **票务员** | 管理员建号（绑定票务员档案） | 窗口代客售票、检票核销、本人售票记录 | 票务员端工作台 |
| **系统管理员** | 内置 / 后台创建 | 景区票种额度管理、订单管理、退票审核、统计报表、用户管理 | 后台管理端 |

**登录与鉴权**：登录态由 Session 承载（Cookie `_session`，30 分钟滑动过期）；后端 Session 中间件拦截 `/api/**`（放行 `login/register/logout/enums/area` 与 CORS 预检），`auth.role:{admin|operator|visitor}` 中间件做接口级角色校验；前端按角色渲染菜单并以路由守卫 `meta.roles` 限制专属页面。管理员**不参与购票**（无购票入口 + 接口硬拒绝）。购票支持**线上自助**与**窗口代客**两渠道，订单以 `channel` 区分，共用同一套库存校验与出票逻辑。

## 3. 业务流程

### 3.1 线上购票主流程

```
游客登录 → 选择票种 / 游园日期 / 数量 → 提交订单（校验：票种在售 / 日期开放 / 额度充足）→ 待支付
   → 模拟支付 → 已支付（出票）：按数量生成门票（每张含唯一核销码 + 二维码）
   → 游客端"我的订单与门票"查看、出示门票
```

订单状态：`待支付 → 已支付 → 已使用`；异常：`已取消 / 退款中 / 已退款`。门票状态：`未检票 → 已检票`；异常：`已退款 / 已过期`。

### 3.2 现场票务与检票流程

```
票务员"现场售票"：选票种 / 日期 / 数量 → 登记线下支付 → 提交即出票（channel=窗口）
游客检票：凭核销码（或扫码）→ 票务员"检票核销"
   → 校验：门票存在 / 游园当日有效 / 状态未检票 → 通过则 已检票（订单核销齐后标记已使用）
   → 失败给出原因：已检票 / 已退款 / 非当日 / 核销码不存在
```

### 3.3 退票与退款流程

```
游客（游园日之前）对未检票门票提交退票申请（原因 + 金额=实付单价）→ 待审核
   → 管理员审核：通过 → 门票已退款、自动回补当日额度（整单退完则订单已退款）
                 驳回 → 写明原因，门票状态不变
   → 同一票不允许多条在途申请；游客可撤回"待审核"申请（撤回后订单状态按票态恢复）
   → 已检票 / 已过期门票不可申请（接口层拒绝）
```

退款状态：`待审核 → 已通过 / 已驳回`；游客撤回置为 `已撤回`（可重新申请）。

> 退款口径：本期为业务层面的退款登记（金额回记），不做真实资金退回；以单票维度登记，整单状态按"全部门票均已退款"归集。

### 3.4 门票改期与游园评价流程

```
门票改期（F03 扩展）：已支付订单在游园日未到前申请改期
   → 校验：目标日期开放 / 新日额度足够 → 同一事务内：原日回补 + 新日占额 + 门票订单游园日更新
   → 门票状态与核销码不变，改期后仍可检票 / 退票；已检票 / 已退款门票不迁移

游园评价（F16）：门票已检票（游园完成）→ 提交评价（星级 1-5 + 短评选填）
   → 校验：本人门票 / 已检票 / 一票一评 → 首页"游园人说"公开展示（昵称脱敏：张三 → 张*）
```

## 5. 增强功能

### E1 每日额度库存校验与防超卖 【核心保障】

- 下单 / 出票 / 改期时基于"游园日期 × 票种"的额度占用表（`ticket_stock.sold_count`）做库存校验，返回可售 / 超售结论与原因（停售 / 非开放日 / 额度不足）；
- **防超卖**：同一事务内完成"校验 + 占额"，先 `lockForUpdate` 锁定额度行再检查累加，配合唯一约束与状态校验，保证"票不超过额、量不多于付"。

### E2 运营数据可视化看板 【管理端】

图表看板（手写 SVG 组件，无第三方图表库），统一筛选：时间范围、票种、渠道——

| 图表 | 类型 | 指标 |
| --- | --- | --- |
| 售票量趋势 | 折线图 | 近 30 天售票张数与订单数 |
| 票种结构 | 环形图 | 各票种销售占比 |
| 收入统计 | 双轴柱线图 | 各票种 / 各渠道（线上、窗口）月度销售额与订单数 |
| 入园与核销率 | 柱状图 + 折线图 | 各日期入园人次、出票—检票核销率 |
| 退票情况 | 柱状图 + 仪表盘 | 退票张数、退票率、审核通过率 |
| 我的购票概要（游客端，F04） | 统计卡 + 折线 / 环形 | 本人累计订单、在用门票、累计消费 + 近 10 日消费趋势 + 票种消费占比 |

## 7. 接口设计约定

- 基础路径 `/api/**`，返回 JSON，统一响应体 `{code, message, data}`（`code=200` 成功）；
- 认证：Cookie Session（`_session`），未登录 / 过期返回 `401`；CORS 中间件放行本地开发来源，前端 `fetch` 以 `credentials: 'include'` 携带会话；
- 参数校验：控制器内 `$request->validate()`（字段名中文化提示），全局异常渲染统一转为 `{code, message}`；
- 角色数据范围：`/my`（游客本人）、`/mine`（票务员经办）、无后缀（管理员全量检索），服务端按登录角色过滤。

路由分组概览（完整定义见 `back-end/routes/api.php`）：

| 分组 | 路径 | 说明 |
| --- | --- | --- |
| 会话与账号 | `/api/auth/*`（register / login / logout / me / password）、`/api/enums` | 注册登录、本人信息、字典枚举（公开） |
| 公开数据 | `/api/area`、`/api/reviews`（GET） | 景区信息 + 开放日 + 票种余量；首页公开评价 |
| 基础数据维护（管理员） | `/api/users` `/visitors` `/operators` `/open-days` `/ticket-types` `/stocks`（RESTful CRUD） | 用户 / 档案 / 开放日 / 票种 / 额度管理 |
| 购票与订单 | `POST /api/orders`；`POST /api/orders/{id}/pay` `/cancel` `/reschedule`；`GET /api/orders/my` `/mine`、`GET/POST /api/orders` | 下单（E1 校验）、支付 / 取消（回补）/ 改期（原日回补 + 新日占额）、三端数据范围区分 |
| 门票与检票 | `GET /api/tickets`、`GET /api/tickets/order/{orderId}`、`POST /api/tickets/check` | 门票检索（管理员）、订单门票明细 / 二维码内容、核销（票务员） |
| 退票 | `GET/POST/DELETE /api/refunds`（`/{id}` 为游客撤回）、`GET /api/refunds/pending`、`PATCH /api/refunds/{id}/audit` | 申请（同一票不重复提交）/ 撤回（游客）、待审核列表与审核（管理员，通过自动回补额度） |
| 评价 | `POST /api/reviews` | 游客对已检票门票提交（一票一评） |
| 统计 | `/api/operator/workbench`、`/api/statistics/overview` | 票务工作台概览（票务员）；看板报表数据（管理员） |

## 8. 非功能需求与技术方案

**技术方案**：前后端分离 B/S；**前端** Vue 3（组合式 API）+ Vite 6 + Vue Router + Pinia（原生 `fetch` 封装 `api()`；图表为手写 SVG 组件）；**后端** Laravel 12（PHP ≥8.2）+ Eloquent ORM，MVC 分层（`Controllers` + `Support\TicketingService/Formatter` + `$fillable` 保护的 Models），Session（30 分钟滑动过期）+ bcrypt；**数据** MySQL 8.x（utf8mb4，库名 `scenic_ticket`），`php artisan migrate --seed` 一键复现；部署：前端 `npm run build` 静态托管，后端 `php artisan serve`（生产可 Nginx + PHP-FPM）。

非功能要求：

| 类别 | 要求 |
| --- | --- |
| 性能 | 主要页面首屏 ≤ 3s；列表接口响应 ≤ 1s（分页 + 索引）；下单库存校验事务内 ≤ 500ms |
| 兼容性 | Chrome / Edge / Firefox 两大版本；≤768px 移动端响应式（游客端体验优先） |
| 安全 | 前后端双向校验；Session + `auth.role` 角色拦截；bcrypt 密码；参数绑定防 SQL 注入、XSS 转义；核销码仅购票人本人与管理端可见 |
| 可靠性 | 关键写操作（下单 / 出票 / 核销 / 审核）事务保证；库存防超卖（行级锁）；统一异常与友好提示 |
| 易用性 | 表单即时校验、空态 / 加载态、关键操作二次确认、状态色标化 |
