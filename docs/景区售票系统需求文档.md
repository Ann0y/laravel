## 1. 项目概述

### 1.1 建设目标

面向中小型景区，构建一套 B/S 架构的售票与票务管理系统，替代"窗口排队买票 + 纸质门票 + 手工统计"的传统售检票方式，实现：

- **统一入口**：票种浏览、在线购票、检票核销、退票审核等业务集中在一个平台办理，信息一次录入、多处复用；
- **全程闭环**：购票 → 出票 → 检票 → 退票（/ 退款），全流程状态可视、可追溯；
- **限量可控**：按"园区开放日 × 票种"设置每日售票额度，售票时做库存校验与防超卖控制，避免超量入园；
- **检票有序**：游客凭订单生成的门票核销码（二维码 / 编码）入园，检票员核销时校验有效期与使用状态，防止重复使用；
- **数据决策**：ECharts 看板呈现售票量、入园量、退票率、收入等关键指标，辅助经营决策；
- **自助服务**：游客可自助查询购票记录、门票状态与核销情况，并在线申请退票。

### 1.2 适用范围边界

| 纳入范围 | 不纳入范围 |
| --- | --- |
| 景区信息、票种与价格、每日售票额度、在线购票、订单、门票核销、退票审核、统计报表 | 与微信 / 支付宝等真实支付网关的对接（本期以模拟支付完成订单状态流转） |
| Web 端（PC + 移动端自适应） | 独立原生 App / 微信小程序 / 闸机硬件对接 |
| 规则型的每日额度库存校验与防超卖 | 基于历史数据的客流预测与动态定价模型 |
| 游客 / 票务员 / 管理员三端功能 | 多景区（集团化）统一票务管理 |
| 二维码门票（页面出示，截图 / 编码备用） | 门票短信下发 / 电子发票开具 |

> 本期为**精简版本**，聚焦核心业务闭环；被裁剪的非必要功能见 **附录 A**，后续按需扩展。

## 2. 用户角色与入口

| 角色 | 来源 | 核心职责 | 入口与可见功能 |
| --- | --- | --- | --- |
| **游客** | 前台自助注册 / 后台建号 | 浏览票种、在线购票、查询订单与门票、申请退票 | 游客端：景区与票种、在线购票、我的订单与门票、个人中心 |
| **票务员** | 管理员后台建号（与票务员档案绑定） | 窗口代客售票、检票核销门票、查看本人售票记录 | 票务员端：票务工作台、现场售票、检票核销、我的售票记录 |
| **系统管理员** | 内置 / 后台创建 | 景区与票种管理、售票额度管理、订单管理、退票审核、统计报表、用户管理 | 后台管理端：工作台 + 全部后台功能 + 统计报表 |

**登录与鉴权**：登录态由 **Session** 承载（Cookie 中的 `JSESSIONID`），默认有效期 30 分钟，采用**滑动过期**实现无感刷新；后端通过 `LoginInterceptor` 拦截 `/api/**`（放行 `login/register/logout` 与 CORS 预检），**仅校验"是否已登录"**，不做接口级角色鉴权。前端按登录角色渲染不同入口与菜单，并通过路由守卫限制各角色专属页面。

> 权限说明：本期以**角色字段 + 前端路由守卫**实现权限区分，不做接口级角色校验与细粒度权限点；RBAC 权限模型列入后续扩展。

> 数据可视化入口说明：按任务书"前端界面至少包括…数据可视化"的要求，**游客端与管理员端均具备可视化**——游客通过"我的订单与门票"页的统计卡呈现本人购票概要（F04），管理员查看工作台指标与统计报表（E2）；完整图表看板以管理端 E2 为主承担。

> **购票渠道说明（重要）**：本期支持**线上自助购票**（游客本人下单）与**窗口代客购票**（票务员为游客下单、登记线下支付）两种渠道，订单以 `channel` 字段区分；两种渠道使用同一套库存校验与出票逻辑。

## 3. 业务流程

### 3.1 线上购票主流程

```
游客注册（或管理员建号） → 登录 → 浏览景区信息与在售票种（选择票种 / 游园日期 / 数量）
   → 提交订单（服务端校验：票种在售 / 游园日期开放 / 库存额度充足）
   → 订单状态：待支付
   → 模拟支付成功 → 订单状态：已支付（出票）
   → 按购买数量生成门票（每张含唯一核销码 + 二维码）
   → 游客端"我的订单与门票"可查看门票与二维码
```

订单状态：`待支付 → 已支付 → 已使用`；异常状态：`已取消 / 已退款 / 退款中`。
门票状态：`未检票 → 已检票`；异常状态：`已退款 / 已过期`。

### 3.2 现场票务与检票流程

```
票务员在"现场售票"为游客选择票种 / 游园日期 / 数量，登记线下支付方式
   → 服务端同一套库存校验 → 提交即视为支付成功：订单状态：已支付（出票），channel=窗口
   → 游客检票：凭门票二维码 / 核销码
   → 票务员在"检票核销"输入核销码（或扫码）→ 校验：门票存在、游园日期当日有效、状态为"未检票"
   → 校验通过：门票状态 → 已检票，订单整体生成完整出票核销记录后可标记已使用
   → 校验失败给出原因（已检票 / 已退款 / 非当日 / 核销码不存在）
```

### 3.3 退票与退款流程

```
游客（游园日之前）在"我的订单"选择未检票门票提交退票申请（说明原因，退款金额=实付单价）
   → 退款状态：待审核
   → 管理员审核退票申请
      → 通过：门票状态 → 已退款，订单回补库存额度，退款状态 → 已通过；
              整单均已退款 / 取消时订单状态置为：已退款
      → 驳回：需说明原因，退款状态 → 已驳回，门票状态不变
   → 已检票 / 已过期门票不可申请退票（接口层校验拒绝）
```

退款状态：`待审核 → 已通过 / 已驳回`。

> 退款口径：本期为**业务层面的退款登记**（金额回记），不通过支付渠道做真实资金退回；整单退 / 差异退（部分票退）以单票维度登记，订单状态按"全部门票均已退款"判断归集。

## 5. 增强功能

### E1 每日额度库存校验与防超卖 【增强功能 · 核心保障】

- 下单 / 出票时，基于"游园日期 × 票种"的额度占用表（`ticket_stock.sold_count`）做库存校验；
- 返回可售 / 超售结论与原因（票种停售、非开放日、剩余额度不足）；
- **防超卖控制**：同一事务内完成"校验 + 占额"（先按主键锁定额度行再检查并累加），配合唯一约束与状态校验，避免并发下单把额度击穿；
- 目的：保证"票不超过额、量不多于付"，订单与额度数据一致。

### E2 运营数据可视化看板 【增强功能 · 对应任务书"数据可视化"界面要求】

ECharts 图表清单：

| 图表 | 类型 | 指标 |
| --- | --- | --- |
| 售票量趋势 | 折线图 | 近 12 个月 / 近 30 天售票张数与订单数 |
| 票种结构 | 饼图 / 环形图 | 各票种销售占比 |
| 收入统计 | 双轴柱线图 | 各票种 / 各渠道（线上、窗口）月度销售额与订单数 |
| 入园与核销率 | 柱状图 / 折线图 | 各日期入园人次、出票—检票核销率 |
| 退票情况 | 柱状图 + 仪表盘 | 退票张数、退票率、审核通过率 |
| 我的购票概要（游客端） | 统计卡 / 迷你图 | 游客本人累计订单数、在用门票数、最近入园时间（任务书要求前端亦有数据可视化） |

支持统一筛选：时间范围、票种、渠道。

## 6. 数据库设计（详细）

### 6.1 设计约定

| 约定项 | 规则 |
| --- | --- |
| 数据库 / 字符集 | MySQL 8.0，库名 `scenic_ticket`，字符集 `utf8mb4`，引擎 InnoDB |
| 主键 | 所有表统一使用 `id BIGINT` 自增主键 |
| 命名 | 表名、字段名小写下划线；唯一约束前缀 `uk_`，普通索引前缀 `idx_`，外键前缀 `fk_`；预留字表名避免使用 `order`（采用 `sale_order`） |
| 时间 | 统一 `DATETIME`；仅日期用 `DATE`，仅时段用 `TIME`；`create_time` 默认 `CURRENT_TIMESTAMP` |
| 金额 | `DECIMAL(10,2)` |
| 逻辑删除 | **主数据表**（`sys_user` / `visitor` / `operator` / `scenic_area` / `ticket_type` / `ticket_stock`）统一含 `del_flag TINYINT DEFAULT 0`（0 正常 / 1 删除）；**业务流水表**（`sale_order` / `ticket` / `refund_record`）不物理、不逻辑删除，仅通过状态字段流转保留痕迹 |
| 敏感信息 | 游客身份证号（优惠购票实名需要）加密存储（AES），列表展示脱敏（保留前 6 后 4）；口令 BCrypt 单向加密 |
| 冗余计数 | `ticket_stock.sold_count`、`sale_order.ticket_count` 为**冗余缓存字段**，由业务写入时同步更新，查询性能优先，允许与明细短暂不一致 |

### 6.2 表清单与实体关系

| 表名 | 说明 | 类型 |
| --- | --- | --- |
| `sys_user` | 登录用户（管理员 / 票务员 / 游客） | 主数据 |
| `visitor` | 游客档案 | 主数据 |
| `operator` | 票务员档案 | 主数据 |
| `scenic_area` | 景区信息 | 主数据 |
| `open_day` | 园区开放日期 | 主数据 |
| `ticket_type` | 票种（含价格） | 主数据 |
| `ticket_stock` | 每日售票额度 | 主数据 |
| `sale_order` | 售票订单 | 流水 |
| `ticket` | 门票（含核销码） | 流水 |
| `refund_record` | 退票申请与审核 | 流水 |

**实体关系**：

- `sys_user` 1 — 1 `visitor`（`visitor.user_id`）
- `sys_user` 1 — 1 `operator`（`operator.user_id`）
- `scenic_area` 1 — N `open_day`（`open_day.area_id`，本期单景区恒为 1 条关系，保留扩展）
- `ticket_type` 1 — N `ticket_stock`（`ticket_stock.type_id`）；`open_day` 1 — N `ticket_stock`（`ticket_stock.open_date` 与开放日对齐）
- `visitor` 1 — N `sale_order`；`ticket_type` 1 — N `sale_order`
- `sale_order` 1 — N `ticket`（按数量出票）；`ticket_type` 1 — N `ticket`
- `ticket` 1 — N `refund_record`（一票可多次申请，最新一条生效）
- `sys_user`（票务员）1 — N `sale_order`（`sale_order.operator_id`，窗口渠道经办人）

## 7. 接口设计约定

- 基础路径：`/api/**`，全部返回 JSON，统一封装 `{code, message, data}`（`code=200` 表示成功）；
- 认证：基于 Cookie 的 Session（`JSESSIONID`），未登录 / 会话过期返回 `code=401`；跨域通过 `WebConfig` 的 CORS 配置放行本地来源并 `allowCredentials=true`，前端 Axios 需 `withCredentials=true`；
- 参数校验：`@Valid` + 全局异常处理器（`GlobalExceptionHandler`）统一转换为 `{code, message}`；
- **角色过滤**：`/api/orders` `/api/tickets` 等三端共用的资源，通过 `/my`（本人）、`/mine`（经办 / 本人票务数据）区分数据范围，服务端按登录用户角色与身份过滤。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/auth/register` `/api/auth/login` `/api/auth/logout` | 注册 / 登录（建立 Session）/ 登出（销毁 Session） |
| GET | `/api/auth/me` | 当前登录用户信息 |
| PUT | `/api/auth/password` | 修改本人密码（校验原密码） |
| GET/POST/PUT/DELETE | `/api/users` `/api/users/{id}` | 用户管理 + 角色分配（管理员） |
| GET/PUT | `/api/enums` | 字典枚举读取（票种编码 / 状态 / 渠道等，后端常量） |
| GET | `/api/area` | 游客端公开：景区信息、开放日期与票种可售情况 |
| GET/POST/PUT/DELETE | `/api/visitors` `/api/visitors/{id}` | 游客档案增删改查（管理员） |
| GET/POST/PUT/DELETE | `/api/operators` `/api/operators/{id}` | 票务员增删改查（管理员） |
| GET/POST/PUT/DELETE | `/api/open-days` `/api/open-days/{id}` | 园区开放日维护（管理员） |
| GET/POST/PUT/DELETE | `/api/ticket-types` `/api/ticket-types/{id}` | 票种增删改查（管理员） |
| GET/POST/PUT/DELETE | `/api/stocks` `?openDate=&typeId=` | 每日售票额度维护与查询（管理员） |
| GET | `/api/operator/workbench` | 票务工作台概览（F05） |
| GET/POST | `/api/orders/my` | 我的订单（游客，按本人过滤，分页 + 状态筛选） |
| GET | `/api/orders/mine` | 我经手的订单（票务员，窗口渠道 + 检票记录） |
| GET/POST | `/api/orders` `?orderNo=&status=&channel=&visitDate=&page=` | 全量订单检索（管理员，多条件组合 + 分页） |
| POST | `/api/orders` | 提交订单（含库存校验 E1；窗口渠道由票务员代客提交） |
| POST | `/api/orders/{id}/pay` | 模拟支付（校验待支付状态并完成出票） |
| POST | `/api/orders/{id}/cancel` | 取消待支付订单（额度回补） |
| GET | `/api/tickets/order/{orderId}` | 订单门票明细与二维码内容（游客 / 管理员） |
| GET | `/api/tickets` `?ticketNo=&orderNo=&visitDate=&page=` | 门票检索（管理员） |
| POST | `/api/tickets/check` | 检票核销（票务员：核销码 → 校验 → 状态置已检票） |
| GET/POST | `/api/refunds` | 退票申请（游客提交 / 撤回；F04） |
| GET | `/api/refunds/pending` | 待审核退票列表（管理员） |
| PATCH | `/api/refunds/{id}/audit` | 退票审核（通过 / 驳回，自动回补库存） |
| GET | `/api/statistics/overview` `?start=&end=&typeId=&channel=` | 看板 / 报表汇总数据 |
